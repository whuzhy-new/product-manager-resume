# AI / Agent 产品专项

## 合格项目的最低证据

1. 有真实用户、任务和业务场景；
2. 说明为什么普通规则或传统功能不足；
3. 有从输入、检索/推理、工具执行到结果反馈的完整链路；
4. 说明用户本人负责的环节与关键判断；
5. 有评测、实际试用或可复现的验证；
6. 考虑失败、超时、重试、权限、降级或人工确认。

只有聊天、天气、文本生成等练习 Demo，若没有真实任务闭环，不应包装成成熟 AI 产品。

## 技术词必须对应产品判断

- **RAG**：文档类型、切分、检索、重排、引用、无结果处理和评测如何影响可信度；
- **Agent / Workflow**：何时由模型决策、何时固定流程，如何控制状态、冲突和结果汇总；
- **Tool / MCP / Skill**：如何发现、加载、授权、调用、持久化和治理，为什么不是简单接口接入；
- **Prompt / Context / Memory**：改变了什么行为，如何验证，副作用是什么；
- **模型选择**：质量、延迟、成本、上下文和工具调用能力之间如何取舍。

没有这些判断时，删掉技术名词比堆词更可信。

## 场景应用故事

适合证明：场景发现、用户洞察、方案封装、任务闭环、采用与效果。

推荐链路：

`Query/访谈/业务信号 → 场景优先级 → Agent 角色与能力组合 → 交互和首轮引导 → 评测与迭代 → 使用或业务结果`

## 平台基建故事

适合证明：共性抽象、资产管理、运行时机制、连接治理、成本和可扩展性。

推荐链路：

`平台缺口 → 用户/生态受阻 → 现有架构限制 → 备选方案比较 → 元信息/加载/调用机制 → 灰度与治理`

## 评测表达

至少写清：

- 任务集来源和样本量；
- 评测维度与判定标准；
- 失败类型，如错路由、漏工具、检索无结果、格式失败、幻觉、超时；
- 针对失败做的 Prompt、描述、首轮提示、路由或工具调整；
- 前后差异与仍未解决的问题。

“准确率提升 40%”只有在能解释样本、基线、指标和计算方法时才可使用。

## 高价值负证据

优秀 AI 项目不只写成功路径。可写清：何时重试、何时降级、何时拒答、何时人工确认、如何记录 Trace、如何观察长期效果。这些往往比多一个技术名词更能证明产品成熟度。
