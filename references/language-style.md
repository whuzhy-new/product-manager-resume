# 产品经理简历语言风格手册

## 目标语气

产品经理简历应当像一份经过压缩的业务判断记录：直接、具体、克制、可追问。它不是岗位说明书、PRD 摘要、汇报材料或营销文案。

合格语言同时满足：

- **读得快**：一句只承担一个中心判断，先出现具体对象和问题；
- **看得懂**：公司黑话、技术词和方法名都能翻译成外部读者理解的业务含义；
- **信得过**：动词与真实责任一致，数字有来源，结果不过度归因；
- **问得深**：每句话都能继续追问“依据是什么、为什么这样做、你具体做了什么、如何验证”。

## 信息密度，不是字数密度

高信息密度指每个短语都在提供新信息，不是把更多名词塞进一句话。

一条内容通常保留以下 2–4 项：

1. 服务对象或业务场景；
2. 明确问题或目标；
3. 判断依据或关键取舍；
4. 本人动作；
5. 验证方法或结果。

同一句出现三个以上并列动作、两个以上括号或连续堆叠技术名词时，优先拆句或删掉常规流程。

## 句子起笔

优先从能够建立业务上下文的信息起笔：

- `针对……问题`：问题清晰时；
- `基于……证据`：判断依据是亮点时；
- `面向……用户/场景`：用户与场景具有区分度时；
- `为实现……目标`：业务目标明确时；
- `在……约束下`：平台、合规、成本或时间取舍是亮点时。

少用“负责、参与、协助”作为空洞开头。若必须说明责任，紧跟具体范围：`负责合同审阅 Agent 的评测迭代`，不要只写`负责产品设计`。

## 六类句子骨架

骨架用于检查信息是否完整，不要求逐字套用。

### 1. 场景发现

`基于[Query/访谈/数据]识别[用户在具体场景中的问题]，将[场景 A]排在[场景 B]之前，原因是[价值或约束]。`

### 2. 需求判断

`拆解[原始需求]后发现核心矛盾是[问题]而非[表象]，因此将方案从[旧方向]收敛为[新方向]。`

### 3. 方案取舍

`在[成本/时间/架构/合规]约束下，对比[备选方案]，选择[方案]并暂缓[未做事项]，以[验证方式]控制风险。`

### 4. 平台机制

`针对[多角色/多场景]的共性问题，抽象[资产模型、接入机制或治理规则]，支持[覆盖范围]并降低[重复成本或上下文成本]。`

### 5. AI 评测迭代

`在[样本量/任务集]中定位[失败类型]，通过[Prompt、描述、路由、检索或工具调整]迭代，并以[指标与口径]验证前后差异。`

### 6. 交付与影响

`推动[明确范围]完成[灰度/上线/验收]；在[时间窗/样本范围]内观察到[结果]，同时保留[负向指标或后续问题]。`

不要强迫每条同时包含背景、动作、结果。一个项目的 2–4 条内容合起来形成完整证据链即可。

## 动词强度与责任边界

### 责任层级

| 表达 | 使用条件 | 需要补充 |
|---|---|---|
| 主导 | 对目标、关键取舍和推进结果承担主要责任 | 主导范围与关键决策 |
| 负责 | 独立承担一个清晰模块、阶段或指标 | 对象、范围和交付 |
| 共同设计 | 与他人共享方案所有权 | 本人具体负责的部分 |
| 推动 | 通过协调或决策使事项前进 | 卡点、协作方和结果 |
| 参与 | 只承担局部工作 | 必须改写成具体动作，不能单独出现 |
| 支持 | 提供分析、材料或能力支持 | 支持对象及被采用方式 |

禁止仅为了显得更强，将“参与”升级为“负责”，或将“负责模块”升级为“主导项目”。

### 精确动作词

- 发现问题：访谈、抽样、拆解、聚类、归因、复盘、定位；
- 作出判断：判定、排序、收敛、取舍、定义、划分、选择；
- 设计方案：抽象、分层、重构、编排、封装、配置、设计；
- 推进交付：对齐、协调、排期、推动、灰度、验收、发布；
- 建立验证：构建、标注、回归、监控、对照、复算、验证；
- 形成影响：覆盖、缩短、降低、提升、沉淀、复用、支持。

动词后必须有具体宾语。`完成优化`信息量低；`重构合同风险标签与批注链路`才可追问。

## 结果语言

### 有直接指标

不要写裸百分比。优先交代：

`基线/对照 + 指标定义 + 结果 + 样本或时间窗`

例如：`灰度 20% 流量两周后，任务完成率由 A 提升至 B；全量后继续保留长期观察桶。`

### 没有直接指标

使用真实的替代证据：

- 交付：进入排期、完成灰度、通过验收、按期发布；
- 范围：用户数、业务线、角色、场景、任务或数据量；
- 效率：时间、步骤、人工投入、处理周期；
- 质量：任务成功、准确、覆盖、缺陷、投诉或评测结果；
- 采用：被业务方使用、复用、纳入标准或支持决策；
- 学习：测试发现的问题、迭代轮次和前后变化。

不以“成功上线”作为自动成立的结果；上线只是状态，使用与效果需要另外证明。

## 项目小标题与标签

标签用于帮助五秒扫读，应命名为真正的能力或问题：

- 推荐：`场景选择`、`工具调用优化`、`评测体系`、`资产发现机制`、`长期效果监控`；
- 不推荐：`产品设计`、`项目推进`、`能力建设`、`综合提升`、`端到端闭环`。

一个项目通常使用 2–4 个小标题。标签过多会把简历变成关键词墙。

## 不同方向的语言重心

### C 端产品

多写用户行为、任务路径、体验摩擦和灰度验证；少写后台功能名。语气可以更贴近用户，但仍保持克制。

### B 端 / SaaS

多写业务角色、流程节点、权限、异常与效率；使用结构化、边界清楚的语言。避免把页面清单当产品复杂度。

### 平台 / 基建

多写共性问题、抽象对象、接入机制、治理和规模化成本；必须先解释为何需要平台化，再写机制。

### 策略 / 增长

多写业务目标、基线异常、诊断假设、策略杠杆、实验对照、负向指标和长期观察。内部术语首次出现时先翻译成外部可理解的产品语义；使用因果词时尤其谨慎，历史变化不直接写成“带来”。详细方法见 [strategy-pm.md](strategy-pm.md)。

策略项目可以用一行“目标”或“OKR”总领岗位阶段，但应控制为业务、对象和成功方向，不要把背景、算法、方案、结果全部塞进目标行。随后每个项目只保留一条主策略链。

### AI / Agent

多写任务链、能力边界、模型或工具选择、评测和失败治理。技术词第一次出现时即说明它解决什么产品问题。

## 不同资历的语言重心

### 实习生 / 应届生

重点证明观察、分析、交付和学习闭环。可以写局部贡献与小样本测试，不假装拥有公司级战略或最终指标。

### 初中级产品经理

重点证明模块所有权、完整链路、关键取舍和上线后迭代。减少“跟进、对接”，增加问题如何被解决。

### 资深产品经理

重点证明目标拆解、复杂决策、跨团队机制、平台抽象、指标负责与规模化复用。仍须落到关键案例，不能只写宏观口号。

职级感来自责任范围和证据，不来自把动词升级成“统筹、战略、全面主导”。

## 母版与定向版的语言差异

- **母版**：事实完整、语气中性，保留必要背景、责任边界、验证口径和可替换证据；
- **定向版**：不改变事实，只调整项目顺序、能力标签、句子重心和关键词，使目标 JD 更容易识别匹配证据。

定向改写不是复制 JD，也不是把每个项目都写成目标岗位的样子。

## 高频病句与改写方向

| 病句 | 问题 | 改写方向 |
|---|---|---|
| 负责需求分析、原型设计、评审和上线 | 岗位说明书 | 补用户问题、判断依据、关键取舍和验证 |
| 参与竞品分析并提出建议 | 个人贡献和去向不明 | 写分析范围、形成的判断及建议是否采用 |
| 协助团队推动项目顺利上线 | 责任模糊，“顺利”无信息 | 写本人解决的卡点、协作对象和交付状态 |
| 打造行业领先的智能工作台 | 自我评价且无法验证 | 写目标用户、任务、机制和已验证效果 |
| 通过 RAG、Agent、MCP 赋能业务 | 技术名词堆叠 | 写每项技术解决的具体问题与选择依据 |
| 显著提升用户体验 | 指标与场景缺失 | 写哪个任务、什么摩擦、如何验证 |
| 完成从 0 到 1 的端到端闭环 | 范围和贡献不清 | 拆为需求依据、本人负责环节、交付与结果 |
| 转化率提升 20% | 裸数字、因果不明 | 补基线、分母、对照、时间窗和个人贡献 |
| 通过 One Model、LTR、OPM 优化低 U | 只有团队黑话，外部读者无法判断价值 | 先写用户分层、策略环节、选择依据和效果，再按需保留术语 |
| 带动大盘消耗和 GMV 显著增长 | 个人动作直接跳到远端结果 | 区分策略直接指标、项目结果和业务最终结果 |

## 压缩顺序

需要缩短时，依次处理：

1. 删除形容词、自我评价和“顺利、成功、全面”等虚词；
2. 删除岗位默认动作，如开会、写文档、日常对接；
3. 合并同义动作，保留产生判断或结果的那一个；
4. 将公司黑话翻译成外部语义；
5. 删除与目标岗位弱相关、证据弱或重复的项目；
6. 最后才压缩核心问题、关键取舍和验证证据。

## 成稿检查

逐句追问：

1. 这句话的主语隐含为谁，能否看出用户本人负责什么；
2. 动词后是否有具体对象；
3. 是否出现了需求依据或产品判断，而非仅有流程；
4. 结果是状态、证据还是未经证明的归因；
5. 数字能否解释来源与口径；
6. 黑话、技术词和标签能否被外部读者理解；
7. 删除这句话后是否损失一种关键能力证据；若不会，考虑删除。
